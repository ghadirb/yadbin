## Activity publication workflow

Every newly created activity starts in the teacher-review workflow; a student link is created for its intended student, but it is not usable until the teacher publishes the activity:

```text
Create → draft → Teacher Preview → feedback/approval → ready_to_publish → Publish → Student Play
```

`publish_state` expresses this preparation state: `draft`, `testing`, `ready_to_publish`, or `published`. `lifecycle` is separate: it expresses whether an activity is `active`, `ended`, or `archived` after its normal lifetime. For example, a published activity whose assigned students have all finished has `publish_state=published` and `lifecycle=ended`.

Preview uses the exact production question generator (same `gen_version`, same difficulty mode, same question count). It has its own `teacher_preview_sessions` rows, so it never creates a student session, result, progress item, report entry, or metric. A preview has no selected student, so the **class grade** stands in for the student's grade (then the activity's age range as midpoint, then the grade-range midpoint, plus the activity level): a preview plays with the band a typical student of the class receives. A preview link is valid for 24 hours. Existing activities that predate this workflow remain published and playable.

Before the run the teacher sees a summary (type, grade, age, skills, level, difficulty, number of steps, approximate minutes). The run itself happens in the student web app under `/preview/:token` with a «حالت آزمایش معلم» banner and ends on a teacher screen («آزمایش تمام شد») instead of the child's end screen.

Feedback values are `suitable`, `too_easy`, `too_hard`, and `needs_edit`, accepted only after a **completed, non-comparison** preview of the *current* settings.

| feedback | result |
|---|---|
| `suitable`, `too_easy` | `ready_to_publish` (an easy activity is safe; the teacher may still edit it) |
| `too_hard`, `needs_edit` | back to `draft`: edit and preview again |

`POST /activities/:id/publish` unlocks student play. It requires an approved preview **or** the teacher's explicit choice `{ "withoutPreview": true }` («انتشار بدون آزمایش», confirmed in the app); without either the server answers `409 teacher_approval_required` with `details.canPublishWithoutPreview`. That choice is recorded as `preview_feedback = 'skipped'`. The validity period of the activity restarts at publication. Clients that deliberately skip the whole workflow may create with `requiresPreview: false` (published at once).

Editing:
* While the activity is **not published**, any change to difficulty, question count, age/grade range, level or skills clears the preview, the approval and all earlier preview runs, and returns it to `draft` (a stale test can never approve an edited activity). Re-sending identical values changes nothing.
* A **published** activity is never switched back to draft by an edit; difficulty and question count stay locked once a child has started (`activity_in_progress` → «ساخت نسخه جدید»).
* The teacher app's edit screen exposes every setting (title, description, minutes, grade range, age range, level, skills, difficulty, question count).

«مقایسهٔ سطح‌ها»: `POST /activities/:id/preview { "compareMode": "easy|medium|hard" }` plays another level without changing the activity. It is marked as a comparison, never counts as approval, and the system makes no claim that a level suits a child.

## Difficulty (generator v2)
`game_sessions.gen_version` / `teacher_preview_sessions.gen_version` fix the generator when a session is created. `NULL` (every session created before v1.2.x) keeps the unchanged v1 generator, so resuming and re-scoring old sessions never changes their questions. New sessions use `generate-v2.ts`:

* **Band** (`tuningForV2`): preschool–grade 2 → −1, grades 3–8 → 0 (grade 6 is a normal grade), grade 9+ → +1; age fallback ≤7 / 8–13 / ≥14; the activity level nudges it by one step.
* **Memory**: 2–7 items (ceiling 7), display time 2000→1000 ms depending on band and level, reverse recall only at level 3, never in the youngest band, and only on the shortest sequences.
* **Attention**: grid 3×3–5×5, 12 s→5.5 s per item, number of targets rises steadily.
* **Problem solving**: bank levels are borrowed downward first; items are ordered simple → pattern → multi-step.
* **Progression**: inside one pool the difficulty rises smoothly with the item position (never a jump of more than one step between neighbours); tests enforce this for 10-question activities.

## Reports
Only `published` activities count in the dashboard, class report, student history and "open activities". Drafts (`draft`, `testing`, `ready_to_publish`) show only in the class activity list; the dashboard reports their number as `totals.drafts`. Preview runs never appear anywhere.

## Safety rules implemented
* Performance values are **indicators of activity results**, never a diagnosis. No medical/psychological wording.
* Fit (`suitable` / `easier_possible` / `out_of_range` / `unrestricted` / `unknown`) is advisory and never blocks assignment.
* AI receives only the teacher's sentence plus grade/age and anonymous skill labels of an **owned** class/student (no names, no ids, no other class). Its output is re-validated field by field; invalid values fall back to the rule-based draft. Rate limit: 20 drafts/hour/teacher.
* Every endpoint is authenticated and ownership-checked; foreign ids return 404.
* Old data stays valid: migrations are additive. Activities created before migration `0007` remain published and playable; every activity created after this version starts as a draft and is published after a teacher preview (or the teacher's explicit «انتشار بدون آزمایش»). Activities without a range show as «بدون محدوده سنی/پایه».
* The dashboard shows counts and distributions only: no ranking, no per-student comparison.

## Manual test checklist (spec §17)
Teacher
1. Create a class with a grade (and optional age range) → it appears with the grade label on the dashboard.
2. Edit the class grade; edit a student's age/grade (menu ⋮ → «ویرایش سن و پایه»).
3. New activity → choose a template → everything is editable → «تأیید و ساخت» → «آزمایش فعالیت».
4. Complete the preview, select feedback, then «تأیید و انتشار» (or «انتشار بدون آزمایش» with its confirmation). Before publishing, student links remain blocked. Try «مقایسهٔ سطح‌ها» and «ویرایش» (all settings) → preview again.
5. Open the published activity: each student has an advisory fit badge when the activity has a range.
5. Student screen: educational profile + «پیشنهاد فعالیت بعدی» → «ویرایش و ساخت این فعالیت» opens a prefilled form.
6. New activity → «ساخت پیشنهاد با هوش مصنوعی» → write a sentence → draft → «ویرایش و ادامه» → edit → create.
7. Dashboard → «نمای کلی» → try the filters.

Student
8. Open a link → play (online and offline) → result is saved → personal report.

Security / compatibility
9. A second teacher cannot see the first teacher's classes/students/activities/drafts.
10. Activities and classes created with v1.0/v1.1 still open and run; they show no age/grade range.

Automated: `worker` (vitest: API, v1.1, v1.2, scoring, security), `student-web` (typecheck/unit/build), `e2e` (Playwright acceptance scenario), Android unit tests (`V12ModelsTest`, `JalaliTest`, `ApiClientTest`, …) — all run in CI.
